# Agent Bridge protocol v0.1

## Canonical representation

UTF-8 JSON is canonical. The authoritative machine-readable schema ships at
`src/agent_bridge/protocol/schema.json` and is included in wheels. Its identifier
is `urn:agent-bridge:protocol:0.1`, using JSON Schema Draft 2020-12.
`python tools/generate_schema.py --check` detects stale generated schemas.

All envelope fields are required; fields without a value use `null` as described
below. Unknown envelope/payload fields are rejected. Vendor additions use
`extensions`. Strings with nonempty requirements must contain a non-whitespace
character. JSON duplicate keys, non-finite numbers, non-JSON Python types and
messages larger than 1 MiB are rejected; nesting is limited to 64 levels.
Whitespace, key order and number spelling are not identity: replay compares
parsed content. Signatures/canonical cryptographic serialization are not defined.

| Field | Meaning |
| --- | --- |
| `protocol_version` | Exactly `"0.1"`; unknown versions are rejected |
| `message_id` | Unique canonical lowercase UUID for this immutable envelope |
| `project_id` | Canonical lowercase UUID generated by initialization |
| `kind` | `state`, `decision`, `approval`, `task`, `handoff`, `report`, `acknowledgment` |
| `source` | Claimed originating agent/human identifier |
| `destination` | Addressed identifier; only `state` may use `null` for project-wide state |
| `correlation_id` | UUID grouping related messages; task messages use the task ID |
| `task_id` | UUID required for task/handoff/report; inherited by their receipts; null for state/decision/approval |
| `in_reply_to` | Parent message UUID for handoff/report/approval/receipt; null for state/decision/task |
| `timestamp` | Valid UTC date/time ending in `Z`; optional fractional seconds with 1–6 digits |
| `status` | Kind-specific event status below |
| `summary` | Nonempty human-readable description |
| `payload` | Kind-specific structured object |
| `extensions` | JSON object; use namespaced keys such as `org.example.hermes` |

Identifiers contain 1–64 ASCII letters/digits, dots, colons, underscores or
hyphens, beginning with a letter/digit. They are addresses, not paths. UUIDs
have the standard lowercase hyphenated shape; no UUID version is mandated.
The local workflow additionally checks matching parent correlations and task IDs.

## Payloads and event statuses

| Kind | Allowed event status | Required payload fields |
| --- | --- | --- |
| `state` | `active`, `blocked` | `state`: object; `blockers`, `risks`: string arrays; `next_action`: string |
| `decision` | `accepted`, `awaiting_approval` | `rationale`: nonempty string; `requires_approval`: boolean |
| `approval` | `approved`, `rejected` | `rationale`: nonempty string |
| `task` | `pending` | `title`, `description`: nonempty strings; `approval_ids`: unique decision UUID array |
| `handoff` | `handed_off` | `instructions`: nonempty string; `context`: object; `blockers`, `risks`: string arrays; `next_action`: string |
| `report` | `succeeded`, `failed`, `blocked` | `result`: nonempty string; `artifacts`, `blockers`, `risks`: string arrays; `next_action`: string |
| `acknowledgment` | `acknowledged` | Empty object |

Arrays may be empty, but each entry must be a nonempty string. `next_action` may
be empty. `state`, `context` and `extensions` can contain arbitrary JSON values
within the limits. `result` should include execution evidence and validation;
the bridge stores an agent's claim rather than verifying its execution.

For decisions, `requires_approval=true` implies `awaiting_approval`; otherwise
the initial status is `accepted`. Approval resolves a pending decision once.
Local policy requires a requested approval to be addressed to `human:<name>`.

## Task lifecycle and causality

```text
pending --handoff--> handed_off --recipient receipt--> in_progress
in_progress --succeeded report--> awaiting_review --creator receipt--> completed
in_progress --blocked report--> blocked --new creator handoff--> handed_off
in_progress --failed report--> failed --new creator handoff--> handed_off
```

The `task` envelope's immutable event status remains `pending`; `status` displays
the derived **current task status**. The task ID is independent of the initial
message ID. All task-chain envelopes and receipts share `correlation_id=task_id`.
Every reply preserves its parent's `task_id` and `correlation_id`.

1. A task creator chooses its initial recipient and optional `approval_ids`.
   Every referenced decision must already exist in this project.
2. Only the task creator may dispatch a pending/blocked/failed task. Dispatch
   requires all attached decisions to be `accepted` or `approved`.
3. The first handoff replies to the task creation message; a retry replies to
   the latest unsuccessful report. A retry may assign a different agent.
4. The handoff recipient records a receipt before reporting. Only that current
   assignee may report, addressing the creator and replying to the handoff.
5. A successful report awaits creator review. The creator's receipt completes
   the task. Receipt of an unsuccessful report records acknowledgment only.
6. Completed tasks cannot be dispatched/reported again. Create a new task for
   further work. Stale reports and receipts cannot mutate a newer handoff.

A requested approval must be resolved by its addressed human identifier and
reply to the decision, addressing its original source. A receipt never resolves
approval. Rejected decisions remain rejected; propose a new decision/task if
the scope changes. Revocation, cancellation, reassignment during active execution
and review rejection of a successful report are outside v0.1. A creator may
leave an unsatisfactory result awaiting review and create follow-up work.

## Delivery and replay

Messages are immutable and ingested in causal order. Receiving an existing ID
with identical parsed content returns the stored message without adding another
event. Different content under the same ID is a conflict. Unknown parent IDs,
wrong project IDs, broken links and invalid transitions are rejected.

A receipt is addressed back to the sender. Reading an inbox never changes it.
Receipts remove the original addressed message from the default inbox, but it
remains visible with `--all`. Receipts themselves are informational and cannot
be acknowledged, avoiding an infinite receipt exchange. Repeating the same
recipient acknowledgment through the API/CLI returns the original receipt.

The local ingestion sequence is authoritative for replay, even if an incoming
timestamp is older than another event. `created_at` and `updated_at` in projected
tasks/decisions come from their event timestamps and need not be monotonic.
Future transports must preserve causality rather than sorting by timestamps.

## Views and future evolution

Markdown exports embed the exact canonical envelope in a fenced JSON block.
The fence grows when data contains backticks. Import accepts **JSON only**;
Markdown is for reading/passing prepared context, not another writable format.

`status` includes the latest state, decision/task projections, message count,
last event timestamp and recommended next action. The next action prioritizes
pending human decisions, then unfinished tasks. A current report can supply its
own next action; otherwise the lifecycle provides a default.

Consumers must validate the schema with date-time format checking enabled and
enforce workflow semantics independently. New envelope fields/kinds require a
protocol version change; namespaced vendor metadata does not. No opaque chat
history, credential field, shell execution field or provider-specific identity
is required by the protocol.
